# 说写（FlowType）安全模型

[English](security-model.md)

本文说明说写协议 v1 已实现的安全机制。它是实现层面的安全模型，不是第三方独立安全审计，也不承诺能让已经失陷的手机或电脑恢复安全。

## 关键安全结论

| 你可能关心的问题 | 结论 |
| --- | --- |
| 局域网、Wi-Fi、路由器或网关不可信，输入内容还安全吗？ | **在本文所述的端点可信前提下是安全的。** TLS 1.3 加密被接受的文字和图片；二维码固定的 Windows 公钥会阻止中间设备替换自己的服务器证书。 |
| 中间人拿到手机公钥后，能冒充已经绑定的手机吗？ | **不能。** Windows 每次连接都会发送新的随机挑战，手机必须用私钥生成有效签名。公钥只能验证签名，不能生成签名。 |
| 中间设备可以做什么？ | 可以看到连接元数据和 mDNS 在线广播，也可以延迟或阻断连接；不能在不被发现的情况下解密或修改说写接受的正文。 |
| 输入正文是否依赖说写的公网中转？ | **不依赖。** 正文在所选手机和电脑之间直连；访问 GitHub 是独立的在线更新流程。 |
| 仍然需要信任什么？ | 手机、手机当前输入法、电脑和目标应用在完成输入功能时都能接触明文。已经被攻破的端点不在这一安全模型的保护范围内。 |

## 安全目标

说写的安全设计目标是：

- 加密所选 Android 设备与 Windows 电脑之间传输的文字和图片内容。
- 让手机确认正在连接的是二维码对应的 Windows 电脑，拒绝公钥与二维码不一致的服务器。
- 每次连接都认证已经绑定的手机，同时不把可导出的手机私钥放入应用数据库。
- 拒绝重放连接认证消息，以及用同一序号发送不同正文的异常行为。
- 让 Windows 高权限输入进程不处理网络，也不持有长期绑定密钥。
- 不依赖安装包下载路径本身，独立验证在线更新。

这一设计假设 Android 和 Windows 操作系统、用户选择的 Android 输入法以及目标 Windows 应用可信。本文后面的“不能防御什么”会更明确地说明边界。

## 数据路径与信任边界

```text
Android 系统输入法
        |
        v
说写 Android 应用
        |
        |  WSS / TLS 1.3
        v
说写 Windows 主程序（普通用户权限）
        |
        |  受限命名管道
        v
说写 Injector（高权限，不监听网络）
        |
        |  受限 TSF IPC
        v
Windows 当前前台应用
```

输入正文不经过公网中转服务。手机通过可访问的局域网或 Tailscale 地址直接连接用户选择的电脑。应用会另行访问 GitHub 检查和下载更新，但 GitHub 不在输入数据路径中。

## 二维码与首次绑定

Windows 配对二维码包含：

- 协议版本和 Windows 电脑 ID；
- 一个或多个候选 WSS 地址；
- Windows TLS 公钥 SPKI 格式的 SHA-256 指纹；
- 一个使用密码学安全随机数生成的 32 字节一次性配对令牌。

一次性令牌只存在于 Windows 进程内存中。它没有可见的倒计时，但首次绑定成功、关闭或取消配对页面、重新生成二维码时都会立即失效。它不是永久凭据。

绑定过程如下：

1. Android 扫描二维码并尝试其中的候选地址。
2. TLS 握手期间，Android 只接受 SPKI SHA-256 与二维码指纹一致的服务器公钥。
3. Android 在 Keystore 中为这台电脑创建 P-256（`secp256r1`）签名密钥。
4. Windows 发送新的随机挑战。Android 对绑定本次挑战的认证内容签名，并连同一次性令牌和手机公钥一起提交。
5. Windows 验证令牌和签名，保存手机 ID 与公钥，然后令牌失效。
6. Android 只为该绑定保留成功连接的地址，二维码中的其他候选地址不会用于后续自动轮换。双方的绑定关系会一直保留，直到任意一端手工解绑、应用数据被清除、系统重装或所需密钥丢失。

Android 的 `phone_id` 是用于区分设备记录的匿名标识，不是认证凭据。已有 ID 会在重新绑定时保留；没有本地 ID 时，应用使用 Android 设备标识的命名空间 SHA-256 哈希作为稳定 ID，无法取得时才回退到随机 ID。Windows 按 `phone_id` 做幂等更新，重新绑定会替换该设备的公钥并保留已有绑定元数据，不会因为手机名称相同而合并不同设备。

尚未失效的二维码属于敏感信息：获得二维码全部内容的人可能抢在目标手机之前完成一次绑定。配对期间应避免展示或分享二维码，完成后关闭配对页面。二维码本身不包含 Windows TLS 私钥。

## 传输加密与 Windows 身份认证

Windows 服务端使用 `rustls`，只允许 TLS 1.3。由于说写通常连接局域网或 Tailscale IP，而不是稳定的公网域名，因此使用自签名证书。

Android 不依赖系统 CA 列表或主机名匹配来确认这条连接。它会把服务器证书中的 SPKI SHA-256 与二维码取得的固定指纹严格比较。Android 的主机名验证器允许 IP 地址是刻意设计：服务器身份由 SPKI 固定校验建立，而不是由主机名建立。

因此，路由器或路径上的其他设备无法用自己的证书冒充已绑定电脑。网络设备仍能看到 IP、端口、连接时间和大致流量，也可以延迟或阻断连接；但没有被固定的 Windows 私钥，就不能读取或篡改被说写接受的文字和图片帧。

使用 Tailscale 时，Tailscale 还会提供网络层加密。说写自身的 TLS 在 Tailscale 网络上仍然启用，应用身份认证不依赖 Tailscale。

### 本地发现元数据

Windows 会通过 mDNS 广播 `_flowtype._tcp.local.`，让 Android 显示已经绑定的电脑是否在线。局域网内的设备可以从广播中看到电脑 ID、协议版本、地址和端口。这个广播不是身份认证机制。

Android 会忽略绑定数据库中不存在的电脑 ID。匹配的广播只改变在线状态提示，不会替换已经保存的连接地址、TLS 固定指纹或手机绑定。本地攻击者可以观察或伪造这个在线信号，使在线提示不准确；但要让说写接受正文，仍然必须通过固定公钥的 TLS 握手和手机身份认证。

## 手机身份认证与防重放

Android 会为每台绑定电脑分别创建一个 Keystore P-256 签名密钥。应用无法通过 API 导出私钥。为了支持后台自动重连，说写不会要求每次签名都进行生物识别。密钥是否由硬件保护取决于具体 Android 设备。

每次 WSS 连接开始时，Windows 都会生成新的 32 字节随机 nonce。Android 使用 `SHA256withECDSA` 对以下经过域分离的字节序列签名：

```text
flowtype-auth-v1\0{pc_id}\0{phone_id}\0{nonce}
```

首次配对请求还会携带一次性令牌和手机公钥；后续连接只提交手机身份与本次新签名。Windows 使用已经保存的手机公钥验证 DER 编码的 ECDSA 签名。

手机公钥不是秘密，单独拿到公钥不能冒充手机；攻击者还必须用对应私钥生成有效签名。每次连接使用的新 nonce 会让截获的旧认证消息无法在下一次连接中重放。Windows 删除某台手机时也会删除其受信公钥，此后该绑定无法再通过认证。

## 正文与图片完整性

只有完成 TLS 和手机身份认证后，业务消息才会被接受。

说写发送完整文本快照，而不是逐个转发模拟按键。每次活动输入都有会话 ID 和递增序号，Windows 根据已经接受的前后快照计算 Unicode 差异。重复状态是幂等的；同一个序号携带不同正文会被视为协议错误并拒绝。连接恢复后，Android 可以携带最后确认序号和最新完整快照继续活动会话。

这对语音输入很重要：Android 输入法可能修改、替换或删除已经识别的词。完整快照能让 Windows 向手机最新状态收敛，而不是误以为每次识别结果只会在末尾追加。

图片剪贴板传输使用同一条已认证 WSS 连接。请求头包含文件长度和 SHA-256；Windows 在替换剪贴板前会验证摘要、编码格式、字节上限、解码尺寸和像素上限。

协议消息和大小限制详见 [FlowType protocol v1](../protocol/v1/README.md)。

## 本地密钥与正文存储

### Android

- 每台电脑对应的 P-256 私钥由 Android Keystore 持有，不写入应用数据库。
- 草稿和历史正文分别使用 Android Keystore 中的 AES 密钥，以 `AES/GCM/NoPadding` 加密字段。
- 绑定数据库会保存电脑名称、所选地址、电脑 ID、公钥固定指纹和手机公钥信息等应用私有元数据。这些元数据不是秘密，也不宣称进行了单独的字段加密。
- 绑定成功后，数据库中的一次性配对令牌会被清除。
- 清空全部历史时，历史加密密钥也会被删除。
- Android manifest 已禁止应用备份。

正文在显示和同步时必然以明文存在于应用内存中。用户选择的输入法也可能有自己的历史或云端策略，这部分由输入法控制，不属于说写的安全边界。

### Windows

- Windows TLS 身份私钥写入磁盘前，使用当前用户作用域的 Windows DPAPI 加密。
- 证书、公钥、电脑 ID、已绑定手机公钥、设备名称和绑定时间不是秘密，保存在当前用户的应用数据目录。
- Windows 不建立已完成输入的历史。活动正文只在同步期间存在于主程序和 Injector 内存中。
- Injector 诊断日志记录进程 ID、序号、文本长度和错误，不记录输入正文。

DPAPI 保护 Windows 用户边界内的静态私钥，但不能防御已经取得该用户凭据或管理员权限的攻击者。

## Windows 权限边界

说写把网络主程序和需要高权限的输入组件分开：

- `flowtype.exe` 以普通用户权限运行，负责 UI、WSS 服务、TLS 身份、绑定记录和协议状态。
- `flowtype-injector.exe` 以高权限运行，但不监听网络，也不持有长期 TLS 或手机绑定密钥。
- 正式安装后，Injector 只通过已经注册的计划任务启动，而不是接受任意高权限命令行。
- 主程序与 Injector 通过 `flowtype-input-v4` 命名管道通信，DACL 只允许当前用户、Administrators 和 SYSTEM。
- Injector 校验客户端进程 ID 和已安装主程序路径；主程序反向校验服务端进程路径、自报二进制路径、IPC 版本、实例 ID 和高权限状态。
- IPC 只支持固定消息类型，并设置 1 MiB 上限，不提供任意命令、脚本或路径执行。
- Injector 和目标进程中的 Windows 文本服务组件使用独立的 `flowtype-tip-v3` IPC 通道，并拒绝组件版本不一致的连接。

这些措施用于缩小高权限攻击面，但它们不是沙箱，也不试图防御 Windows 管理员；管理员本来就在操作系统信任边界内。

## 在线更新完整性

Windows 和 Android 从 GitHub Releases 获取更新元数据与安装包，但安装决策不只依赖 HTTPS：

1. 客户端使用内置公钥验证独立 P-256 签名的更新清单。
2. 客户端根据已签名清单检查下载文件长度和 SHA-256。
3. Windows 继续验证安装包的 Authenticode 发布者身份；Android 验证 APK 签名证书与已安装的说写应用一致。
4. 最终安装仍需用户通过系统正常流程确认。

更新清单签名密钥与设备绑定身份、Android APK 签名密钥和 Windows Authenticode 证书相互独立。发布和恢复设计详见 [在线更新设计](update-design-v1.md)。

## 这一模型不能防御什么

说写不宣称能在以下情况中保护输入内容：

- 攻击者已经取得 Android root、Windows 管理员或同等端点控制权限；
- Android 当前输入法恶意或已经被攻破；
- 其他软件可以读取屏幕、辅助功能内容、剪贴板、目标应用内存或目标文档；
- 有人能在扫描前替换二维码，或者取得尚未失效的配对二维码并抢先完成绑定；
- 用户选择的 Windows 目标应用，因为输入正文必然要交给它；
- 网络阻断、路由器断电、设备离线或目标应用拒绝文本注入等拒绝服务情况。

说写也无法向本地网络隐藏连接元数据和 mDNS 在线广播。它的目标是保护已接受正文的机密性与完整性、认证两端设备，并限制 Windows 高权限接口范围。

## 用户安全建议

- 直接扫描目标电脑上显示的二维码，绑定完成后关闭配对页面。
- 手机或电脑丢失、转让或不再可信时，在两端删除对应绑定。
- 及时更新 Android、Windows、所用输入法和说写。
- 只从项目的 [GitHub Releases](https://github.com/Henry10088/FlowType/releases) 页面安装正式发布包。
- 向终端、管理员提示、密码框或远程系统输入文字时，同时遵循目标系统自己的安全要求。

报告安全问题时请遵循 [SECURITY.md](../SECURITY.md)，不要在公开 Issue 中附带密钥、配对二维码、私人正文或包含敏感内容的抓包。
