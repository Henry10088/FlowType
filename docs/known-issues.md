# 已知问题与回归记录

## WI-2026-08-30-01：Android 退出前台后仍长期连接 Windows

- **现象**：主界面已经进入后台且未使用浮窗，Windows 仍显示手机在线，手机进程存活期间同步 WebSocket、电脑控制连接和局域网发现持续运行。
- **根因**：连接由 Application 级 `FlowTypeController` 持有，Activity 的 `onStop` 只保存草稿和移除 UI 观察者，没有释放网络资源；后台进程未被 Android 回收时仍会保持心跳并自动重连。
- **修复**：主界面和浮窗输入面板分别持有连接使用权。两者都不可见时等待 500 ms，随后关闭同步连接、所有电脑控制连接并停止 NSD 发现；重新进入主界面或打开浮窗输入面板时立即恢复。只有浮动球可见时不持有连接。
- **回归用例**：覆盖主界面进入后台后断开、500 ms 内返回不抖动连接、只有浮动球时保持离线、打开浮窗输入面板后恢复连接、收起输入面板后再次断开，以及重新进入主界面恢复连接。

## WI-2026-08-30-02：在新光标同步全文时重复追加相同正文

- **现象**：电脑目标末尾已经存在 Android 输入框的完整正文；旧范围停止后，用户把光标放回末尾并点击“同步”，Windows 又追加一份相同全文。
- **根因**：首份 Android 全文在本地链路中被拆成空范围 `Begin` 和后续 `Apply`。TIP 建立新范围时不知道 Android 全文，无法判断紧贴新光标的最后一段是否已经相同。
- **修复**：Android 只有用户在新光标点击“同步”时为 `start` 设置一次性的 `attach_existing=true`；主程序、Injector 和 TIP 的 `Begin` 原子携带首份序号与全文。折叠光标前等长 UTF-16 完全一致时，TIP 只接管最后一段并且不写入；不一致时正常插入。更前面的正文不纳入范围，不做部分匹配、模糊匹配或历史重复清理。普通首次输入、已有范围更新和重连不执行该检查。本地 IPC 分别提升到 Injector v6 和 TIP v8。
- **回归用例**：真实 Notepad++ 先得到 `会议记录：通天通天塔`，随后在末尾以 Android 全文 `通天塔` 点击同步；目标不得增加字符。Android 再改为 `通天大厦` 后，最终必须是 `会议记录：通天通天大厦`。另覆盖非匹配光标正常插入、非 BMP/换行 UTF-16 精确比较、自动首次输入不检查，以及未确认 `start` 重连后保留一次性意图。

## WI-2026-08-29-02：高频输入卡住 Windows UI，换行后全文重新插入

- **现象**：真机逐字或语音输入时，FlowType Windows 窗口随同步状态频繁卡顿；Notepad++ 等宿主在换行后偶发停止替换，后续全文从新光标位置再次插入，形成多段重复内容。
- **日志证据**：Notepad++ 已加载 TIP IPC v4，单一会话的序号连续确认，但包含换行的更新返回 `CompositionTerminated`；Android 保留全文并创建新会话后，Injector 出现 `RebindRejected` 或在新范围接受 `Begin`。同时每个 Injector 请求和 120ms 会话查询即使没有改变状态，也会通知原生 UI 重绘主窗口、托盘和悬浮球。
- **根因**：部分 TSF 宿主在组合范围跨越段落时会自动结束组合态，但原有实现把“组合态结束”等同于“目标文本被外部修改”。已提交到宿主的范围仍然有效，却被丢弃并要求 Android 重建会话。Windows 状态层也没有在通知 UI 前比较新旧状态。
- **修复**：TIP IPC 提升到 v5，组合对象和可追踪文本范围分开管理；宿主结束组合态后继续在同一范围应用完整文本，只有范围内容或光标确实不一致时才停止。Windows 运行状态只在值实际变化时通知 UI。
- **回归用例**：真实 Notepad++ 在同一会话中执行高频追加、换行、跨行替换、缩短和完成，最终只保留最后全文；外部键盘或光标修改仍必须停止会话；无变化的 Injector 成功响应不得触发 UI 刷新。

### 2026-08-30 补充：v5 在组合结束后错误重建会话

- **现场证据**：重启后的 Notepad++ 已加载 TIP IPC v5，但每个新 `session_id` 只应用一次 `seq=1`，健康查询随后把宿主结束组合的回调误判为外部修改；Android 在下一次文字变化时自动创建新会话，完整正文因此从新光标位置再次插入。
- **进一步根因**：Notepad++ 会在 `OnCompositionTerminated` 到达前把原 `ITfRange` 塌缩为空。仅把组合对象和范围分开保存仍不够，下一次更新会把空范围误判为电脑端修改。TIP 返回 `Applied` 时，Scintilla 文档缓冲区也可能尚未提交组合内容，因此不能只用 ACK 判断真实结果。
- **修复**：TIP IPC 提升到 v6。单一 session 始终拥有同一段目标文本；保存范围失效时，以当前折叠光标为右边界，按上一版正文的 UTF-16 长度向左重建候选范围，并读取候选正文校验。只有光标和旧正文同时匹配才继续替换，否则停止会话。不同 session 不得替换未完成范围。真正失败时 Windows 取消旧 TIP 状态，Android 只更新本地草稿，必须明确执行“同步全文”才会选择新插入点；后台恢复、进程重启和覆盖安装不得清除这一门槛。
- **回归用例**：真实 x86 Notepad++ 连续执行 3 轮、每轮 25 次追加、多行、修正和缩短，共 75 次同 session 更新；每轮完成后直接读取 Scintilla 正文，最终只包含 3 份最终稿。不同 session 的 `Begin` 在旧 session 完成或取消前必须失败；服务端拒绝后继续编辑手机正文不得产生新的 `START`，退后台恢复或重启应用后仍需手动同步全文。

### 2026-08-30 补充：空闲 Injector 影响全局手动输入

- **现场证据**：没有活动手机输入时，系统中曾同时驻留两份 Injector；全局低级键盘和鼠标钩子始终启用，活动会话又每 120 ms 查询目标 TIP，逐次成功更新同步写诊断日志。普通键盘输入和 FlowType 窗口因此出现周期性停顿。
- **进一步根因**：进程、输入监听、目标状态轮询和诊断写入都没有严格绑定到手机输入会话生命周期。主程序与 Injector 的 IPC 断开后，Injector 也可能继续持有目标 TSF 会话。
- **修复**：Injector 使用跨版本稳定互斥量保证当前用户只有一个实例；全局输入钩子由活动会话按需持有并通过 RAII 释放；TIP 状态查询限制为每秒一次，120 ms 服务轮询只读取 Injector 本地状态；成功的逐次更新不再同步写日志；主程序 IPC 断开、网络断开超出 1.5 秒重连窗口、取消或完成时都强制结束 TSF 会话并释放钩子。
- **回归用例**：覆盖第二份 Injector 立即退出、空闲时没有已安装输入钩子、会话开始/结束后的钩子启停、IPC 异常断开后的会话清理、短暂网络重连继续原会话，以及空闲状态下持续手动输入不出现周期性卡顿。

## WI-2026-08-29-01：旧驻留 TIP 被误判兼容后重复追加并拖慢手动输入

- **现象**：覆盖安装新版本后，Codex 等安装期间未退出的应用会把每版语音识别结果重复追加，无法按全文状态删除或替换；连续输入后，该应用的普通键盘输入也明显卡顿。
- **日志证据**：同一目标线程在每次 `Update` 成功后立即断开并重新连接 TIP；Android 随后收到会话失效并为下一次文本变化创建新 `session_id`，导致每个完整快照都在新组合范围中插入。
- **根因**：Injector 仅按 TIP IPC 数字判断兼容，却没有在 TIP 会话生命周期实现发生变化时提升该数字。覆盖安装无法卸载目标进程已经加载的旧 DLL，因此 `0.2.7` Injector 接受了仍驻留在 Codex 进程中的 `0.2.6 / TIP IPC v3` 组件。
- **修复**：TIP IPC 提升到 v4，要求一条 TIP 连接完整保持 `Begin -> Update* -> Finish` 会话；v3 客户端不再进入候选集合。被拒绝的旧客户端保持隔离连接直到宿主退出，避免每 200ms 重连影响输入线程。
- **回归用例**：固定拒绝 `0.2.6 / TIP IPC v3`；同一连接依次执行多次追加、替换、缩短和完成，所有响应保持同一 `session_id` 且序号单调递增；覆盖升级后旧宿主不再刷重连日志，新启动宿主加载 v4 并完成真实 TSF 全文替换；完成后手动输入响应正常。

## WI-2026-08-28-01：TSF 启动失败后语音修正重复累加

- **现象**：手机全文不断修正时，Windows 偶发无法替换旧句，而是把多个中间识别结果连续追加；同一版本在应用内开始可用，多次断开、切换或完成后又提示输入服务不可用。
- **根因**：旧注入器在 TIP `Begin` 返回 `SessionMismatch` 或超时后静默切换到 Unicode `SendInput`。该路径只确认系统接收按键，无法确认目标已处理上一批退格和文字，却仍提前 ACK，快速语音修正因此累计错乱。Android 切换电脑时还会取消旧会话，增加 TIP 组合反复关闭和重建的频率。
- **修复**：删除运行时 `SendInput` 回退；主程序到注入器 IPC 升级到 v4，当时 TIP IPC 升级到 v3；TIP 发现窗口扩展到 1.5 秒并重试首选线程；同一 `session_id` 的 Begin 幂等；Android 按电脑独立保存和恢复会话，切换时不发送完成或取消；删除换行自动结束推断。后续驻留 DLL 兼容边界见 `WI-2026-08-29-01`。
- **回归用例**：在同一目标连续发送多版完整语音快照，最终只保留最新版；断开正文 WSS 后重连发送 `resume`；A → B → A 切换后 A 使用原会话 ID 和序号继续；TSF 不可用或组件版本不一致时不写入任何文本并保留手机全文；正文以换行结尾时会话仍保持活动。

## WI-2026-08-27-01：升级或卸载后残留 FlowType 输入法条目

- **现象**：Windows 输入切换界面出现本不应显示的 FlowType 输入法；覆盖升级或卸载后，旧 TIP DLL 和注册表项仍可能保留。
- **根因**：按内容哈希保留 TIP DLL 的升级方案只处理当前 x64 文件名，没有枚举早期版本号命名和 x86 DLL；旧版注册过的 `GUID_TFCAT_TIP_KEYBOARD` 类别也没有在安装器层强制清除。
- **修复**：TIP 注册只保留 `GUID_TFCAT_TIP_SPEECH`，安装前枚举并注销所有历史 x64/x86 DLL，覆盖升级后仅注册当前两种位数的内容哈希 DLL；已被应用加载的旧文件不强制要求重启删除。卸载时再次注销全部历史 DLL，并清除 x64、x86 和当前用户的 FlowType TSF 注册。
- **回归用例**：从包含 `flowtype_tip_0_1_*.dll`、`flowtype_tip_x86_0_1_*.dll` 和键盘类别残项的旧安装覆盖升级；确认 `Win + Space` 不显示 FlowType，x64/x86 Speech 类别正常，随后卸载并确认两种注册表视图和当前用户 Profile 均不存在 FlowType CLSID。

## WI-2026-08-24-09：Windows IoT 缺少 MSVC 运行库

- **现象**：安装程序完成后启动 `flowtype.exe` 报找不到 `VCRUNTIME140.dll`。
- **根因**：Windows MSVC 目标默认动态链接 Visual C++ CRT；Windows 10 IoT 精简环境未预装该运行库。
- **修复**：Windows x64/x86 Release 全部启用 `+crt-static`，安装包不再依赖外部 VC++ Runtime。对应版本：`0.1.13`。
- **回归用例**：在没有 VC++ Redistributable 的 Windows 10 IoT 环境安装并启动；检查主程序、注入服务和 x64/x86 TIP DLL 均可加载。

## WI-2026-08-24-08：Chromium WebView 有 TIP 连接但没有 TSF 文本焦点

- **现象**：`passage_browser.exe` 内嵌 WebView 的文本框可用普通键盘输入，但手机开始输入后提示不支持实时输入。
- **日志证据**：目标 PID 对应 Passage Browser，TIP 已连接；Begin 返回 `NoFocus`，旧版约 3 秒后记录 `tip_failed`，没有建立兼容输入会话。
- **根因**：Chromium 渲染层的文本焦点不一定暴露给宿主进程的 FlowType TIP。故障电脑实际仍运行 `0.1.10`，该版本把“TIP 已连接但没有文本焦点”持续等待后作为失败返回。
- **修复**：`0.1.11` 起统一按能力选择后端，TSF 在 250ms 内无法建立组合文本即使用 Unicode `SendInput`；不按 WebView 或进程名增加分支。本机已就地升级到 `0.1.12`。
- **回归用例**：Passage Browser 打开 ChatGPT WebView 并聚焦文本框；日志应先出现 `TipResponse::NoFocus`，随后出现 `begin mode=legacy_unicode_input` 和成功的 `update ... mode=legacy`；完成后切换到普通 TSF 应用确认输入法状态不变。

## WI-2026-08-24-07：输入后端分支和光标会话边界不一致

- **现象**：Codex、Notepad++ 修复后记事本可能再次无法开始；同一窗口移动光标后，手机仍能修改旧位置；“同步到当前光标”可能被残留 TIP 阻塞。
- **日志证据**：记事本 TIP Begin 连续返回 `SessionMismatch`；兼容后端只检查 HWND，TSF 更新前没有主动复查选区。
- **根因**：后端按应用名选择，而且 TSF 与兼容输入使用不同的会话失效规则。
- **修复**：统一为“TSF 优先、Unicode 输入兼容”的能力选择；两种后端共享真实键鼠输入租约，TSF 每次更新前额外验证组合范围和选区。对应版本：`0.1.11`。
- **回归用例**：记事本、Notepad++、Codex 连续输入；同窗口点击新光标后旧会话停止；点击“同步到当前光标”后全文只进入新位置；仅移动鼠标不停止。

## WI-2026-08-24-04：Codex 主窗口会话残留导致无法重新开始输入

- **现象**：Codex 主窗口第一次输入后，后续输入提示当前应用不支持实时输入；普通窗口可能仍可用。
- **日志证据**：目标 PID 为 `ChatGPT.exe`，TIP Begin 返回 `SessionMismatch`；注入器自身没有活动会话。
- **根因**：TIP 进程内保留了上一次注入器生命周期的组合状态，注入器重连后被错误当成并发会话拒绝。
- **修复**：新 Begin 到达且注入器没有活动会话时，TIP 先结束并清理残留组合，再建立新会话。对应版本：`0.1.8`。
- **回归用例**：Codex 主窗口连续开始两次会话；每次完成后再次输入，确认中文、修正和删除均能同步。

## WI-2026-08-24-05：Notepad++ 语音修正整段重写导致延迟

- **现象**：Notepad++ 每次语音快照更新都删除旧全文再重新注入，文本变长后明显变慢。
- **根因**：兼容路径只能通过 Unicode `SendInput` 操作光标，旧实现没有利用语音修正通常发生在末尾这一事实。
- **修复**：追加、末尾删除和末尾替换只发送变化的尾部；无法确认是末尾编辑时才使用整段替换。对应版本：`0.1.9`。
- **回归用例**：连续追加、末尾修正、末尾删除、中文和 emoji；中间编辑保留保守替换路径。

## WI-2026-08-24-06：Codex 主窗口没有可用 TSF 文档上下文

- **现象**：Codex 主窗口提示不支持实时输入；其它 Codex 子进程可能正常。
- **根因**：主窗口进程为 `ChatGPT.exe`，前台线程不提供可开始组合文本的 TSF 文档上下文。

- **回归用例**：Codex 主窗口连续追加、语音末尾修正、删除和中文输入；完成后切换到普通 TSF 应用确认输入服务状态不变。

## WI-2026-08-24-01：说写主窗口被误当成输入目标

- **现象**：手机单电脑绑定时，点击“同步全文”后立即显示输入停止或同步断开。
- **复现条件**：Windows 的说写主窗口位于前台，实际编辑器窗口在其后方；尤其是从手机开始输入时，说写窗口仍保持打开。
- **日志证据**：
  - `begin target_pid=25604 ...`
  - `begin tip_ready pid=25604 ...`
  - `update ... result=Err("TSF edit timed out")`
  - PID `25604` 对应 `flowtype.exe`，不是目标编辑器。
- **排除项**：这不是网络认证失败，也不是单纯的 32 位 TSF 注册失败。32 位注册失败应表现为“当前应用不支持实时输入”。
- **修复**：目标探测排除说写窗口；当说写窗口前台时，回退到窗口 Z 顺序中最近的外部窗口；RDP 客户端继续排除。对应提交：`97be6a6`、`cafe50e`。
- **验证状态**：本机此前运行 `0.1.4`，x64/x86 CLSID 均已确认；`0.1.7` 已重新构建 x64/x86 DLL 和安装包。手机绑定到其它电脑时，必须在实际绑定的电脑上安装并验证，不能用本机日志代替。

### 发布前回归用例

1. 说写窗口打开并置于编辑器前方，手机开始输入；文本应进入编辑器，不应进入说写界面。
2. 说写窗口最小化后，在 x64 Notepad++、x86 Notepad++、VS Code 和浏览器输入框分别测试。
3. 非全屏 RDP 前台时移动鼠标，自动选择不应把主机 RDP 容器当作输入目标。
4. 在两台已更新电脑之间切换，确认每台电脑都安装同一版本并分别记录 Windows 输入服务日志。

## WI-2026-08-24-02：单电脑自动探测误报无法确定电脑

- **现象**：只有一台绑定电脑时，手机显示“无法确定当前电脑，请手工选择”，Windows 没有收到 `begin` 请求。
- **根因**：Android 对单个候选仍执行前台目标探测；说写窗口或其后方编辑器导致探测结果不是 `READY`，但单候选本身不存在选择歧义。
- **修复**：候选电脑只有一台时跳过竞争探测，直接连接该电脑；Windows 端仍负责最终验证实际文本目标。
- **回归用例**：单绑定电脑、说写窗口打开并覆盖编辑器时，输入应直接建立会话；只有多台自动切换电脑时才执行目标探测。

## WI-2026-08-24-03：Notepad++ 无法建立 TSF 会话（当前回归）

- **现象**：普通 Windows 文本框可以实时同步，Notepad++（x86）开始输入后提示不支持实时输入，文本没有进入编辑器。
- **日志证据**：目标为 `notepad++.exe`，TIP pipe 已连接，但 `begin` 阶段连续超时；普通记事本同一流程能记录 `tip_ready`、`update result=Ok(Applied)`。
- **根因**：Notepad++ 的 Scintilla 编辑控件不提供可供 FlowType 组合文本使用的 TSF 文档上下文。32 位 DLL 已注册且已加载，问题不在安装位数或 WebSocket。
- **修复**：`0.1.10` 及以前曾按 Notepad++ 名称选择 Unicode `SendInput`；`0.1.11` 已改为统一能力选择和会话输入租约。
- **已知边界**：兼容路径依赖目标窗口仍可激活；系统接受输入事件不等于目标应用已经持久化文本。

### Notepad++ 发布前回归矩阵

1. x86 Notepad++：空文档连续追加、语音末尾修正、删除、替换、中文和 emoji。
2. x86 Notepad++：说写窗口前台时开始输入，确认目标仍是 Notepad++。
3. 完成后切换到普通记事本，再开始新会话，确认 TSF 路径仍可用且输入法布局不变。
4. x64 Notepad++（如安装）：与 x86 用例相同，确认兼容路径不依赖位数。
