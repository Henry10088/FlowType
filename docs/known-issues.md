# 已知问题与回归记录

## WI-2026-08-24-09：Windows IoT 缺少 MSVC 运行库

- **现象**：安装程序完成后启动 `flowtype.exe` 报找不到 `VCRUNTIME140.dll`。
- **根因**：Windows MSVC 目标默认动态链接 Visual C++ CRT；Windows 10 IoT 精简环境未预装该运行库。
- **修复**：Windows x64/x86 Release 全部启用 `+crt-static`，安装包不再依赖外部 VC++ Runtime。对应版本：`0.1.13`。
- **回归用例**：在没有 VC++ Redistributable 的 Windows 10 IoT 环境安装并启动；检查主程序、注入服务和 x64/x86 TIP DLL 均可加载。

## WI-2026-08-24-08：Chromium WebView 有 TIP 连接但没有 TSF 文本焦点

- **现象**：`passage_browser.exe` 内嵌 WebView 的文本框可用普通键盘输入，但手机开始输入后提示不支持实时输入。
- **日志证据**：目标 PID 对应 Passage Browser，TIP 已连接；Begin 返回 `NoFocus`，旧版约 3 秒后记录 `tip_failed`，没有建立兼容输入会话。
- **根因**：Chromium 渲染层的文本焦点不一定暴露给宿主进程的 FlowType TIP。故障电脑实际仍运行 `0.1.10`，该版本把“TIP 已连接但没有文本焦点”持续等待后作为失败返回。
- **修复**：`0.1.11` 起统一按能力选择后端，TSF 在 250ms 内无法建立组合文本即使用 Unicode `SendInput`；不按 WebView 或进程名增加分支。本机已就地升级到 `0.1.12`。
- **回归用例**：Passage Browser 打开 ChatGPT WebView 并聚焦文本框；日志应先出现 `TipResponse::NoFocus`，随后出现 `begin mode=legacy_unicode_input` 和成功的 `update ... mode=legacy`；完成后切换到普通 TSF 应用确认输入法状态不变。

## WI-2026-08-24-07：输入后端分支和光标会话边界不一致

- **现象**：Codex、Notepad++ 修复后记事本可能再次无法开始；同一窗口移动光标后，手机仍能修改旧位置；“同步到当前光标”可能被残留 TIP 阻塞。
- **日志证据**：记事本 TIP Begin 连续返回 `SessionMismatch`；兼容后端只检查 HWND，TSF 更新前没有主动复查选区。
- **根因**：后端按应用名选择，而且 TSF 与兼容输入使用不同的会话失效规则。
- **修复**：统一为“TSF 优先、Unicode 输入兼容”的能力选择；两种后端共享真实键鼠输入租约，TSF 每次更新前额外验证组合范围和选区。对应版本：`0.1.11`。
- **回归用例**：记事本、Notepad++、Codex 连续输入；同窗口点击新光标后旧会话停止；点击“同步到当前光标”后全文只进入新位置；仅移动鼠标不停止。

## WI-2026-08-24-04：Codex 主窗口会话残留导致无法重新开始输入

- **现象**：Codex 主窗口第一次输入后，后续输入提示当前应用不支持实时输入；普通窗口可能仍可用。
- **日志证据**：目标 PID 为 `ChatGPT.exe`，TIP Begin 返回 `SessionMismatch`；注入器自身没有活动会话。
- **根因**：TIP 进程内保留了上一次注入器生命周期的组合状态，注入器重连后被错误当成并发会话拒绝。
- **修复**：新 Begin 到达且注入器没有活动会话时，TIP 先结束并清理残留组合，再建立新会话。对应版本：`0.1.8`。
- **回归用例**：Codex 主窗口连续开始两次会话；每次完成后再次输入，确认中文、修正和删除均能同步。

## WI-2026-08-24-05：Notepad++ 语音修正整段重写导致延迟

- **现象**：Notepad++ 每次语音快照更新都删除旧全文再重新注入，文本变长后明显变慢。
- **根因**：兼容路径只能通过 Unicode `SendInput` 操作光标，旧实现没有利用语音修正通常发生在末尾这一事实。
- **修复**：追加、末尾删除和末尾替换只发送变化的尾部；无法确认是末尾编辑时才使用整段替换。对应版本：`0.1.9`。
- **回归用例**：连续追加、末尾修正、末尾删除、中文和 emoji；中间编辑保留保守替换路径。

## WI-2026-08-24-06：Codex 主窗口没有可用 TSF 文档上下文

- **现象**：Codex 主窗口提示不支持实时输入；其它 Codex 子进程可能正常。
- **根因**：主窗口进程为 `ChatGPT.exe`，前台线程不提供可开始组合文本的 TSF 文档上下文。
- **修复**：`0.1.10` 曾仅对 `ChatGPT.exe` 使用 Unicode `SendInput`；`0.1.11` 已由统一的能力选择取代应用名分支。
- **回归用例**：Codex 主窗口连续追加、语音末尾修正、删除和中文输入；完成后切换到普通 TSF 应用确认输入服务状态不变。

## WI-2026-08-24-01：说写主窗口被误当成输入目标

- **现象**：手机单电脑绑定时，点击“同步全文”后立即显示输入停止或同步断开。
- **复现条件**：Windows 的说写主窗口位于前台，实际编辑器窗口在其后方；尤其是从手机开始输入时，说写窗口仍保持打开。
- **日志证据**：
  - `begin target_pid=25604 ...`
  - `begin tip_ready pid=25604 ...`
  - `update ... result=Err("TSF edit timed out")`
  - PID `25604` 对应 `flowtype.exe`，不是目标编辑器。
- **排除项**：这不是网络认证失败，也不是单纯的 32 位 TSF 注册失败。32 位注册失败应表现为“当前应用不支持实时输入”。
- **修复**：目标探测排除说写窗口；当说写窗口前台时，回退到窗口 Z 顺序中最近的外部窗口；RDP 客户端继续排除。对应提交：`97be6a6`、`cafe50e`。
- **验证状态**：本机此前运行 `0.1.4`，x64/x86 CLSID 均已确认；`0.1.7` 已重新构建 x64/x86 DLL 和安装包。手机绑定到其它电脑时，必须在实际绑定的电脑上安装并验证，不能用本机日志代替。

### 发布前回归用例

1. 说写窗口打开并置于编辑器前方，手机开始输入；文本应进入编辑器，不应进入说写界面。
2. 说写窗口最小化后，在 x64 Notepad++、x86 Notepad++、VS Code 和浏览器输入框分别测试。
3. 非全屏 RDP 前台时移动鼠标，自动选择不应把主机 RDP 容器当作输入目标。
4. 在两台已更新电脑之间切换，确认每台电脑都安装同一版本并分别记录 Windows 输入服务日志。

## WI-2026-08-24-02：单电脑自动探测误报无法确定电脑

- **现象**：只有一台绑定电脑时，手机显示“无法确定当前电脑，请手工选择”，Windows 没有收到 `begin` 请求。
- **根因**：Android 对单个候选仍执行前台目标探测；说写窗口或其后方编辑器导致探测结果不是 `READY`，但单候选本身不存在选择歧义。
- **修复**：候选电脑只有一台时跳过竞争探测，直接连接该电脑；Windows 端仍负责最终验证实际文本目标。
- **回归用例**：单绑定电脑、说写窗口打开并覆盖编辑器时，输入应直接建立会话；只有多台自动切换电脑时才执行目标探测。

## WI-2026-08-24-03：Notepad++ 无法建立 TSF 会话（当前回归）

- **现象**：普通 Windows 文本框可以实时同步，Notepad++（x86）开始输入后提示不支持实时输入，文本没有进入编辑器。
- **日志证据**：目标为 `notepad++.exe`，TIP pipe 已连接，但 `begin` 阶段连续超时；普通记事本同一流程能记录 `tip_ready`、`update result=Ok(Applied)`。
- **根因**：Notepad++ 的 Scintilla 编辑控件不提供可供 FlowType 组合文本使用的 TSF 文档上下文。32 位 DLL 已注册且已加载，问题不在安装位数或 WebSocket。
- **修复**：`0.1.10` 及以前曾按 Notepad++ 名称选择 Unicode `SendInput`；`0.1.11` 已改为统一能力选择和会话输入租约。
- **已知边界**：兼容路径依赖目标窗口仍可激活；系统接受输入事件不等于目标应用已经持久化文本。

### Notepad++ 发布前回归矩阵

1. x86 Notepad++：空文档连续追加、语音末尾修正、删除、替换、中文和 emoji。
2. x86 Notepad++：说写窗口前台时开始输入，确认目标仍是 Notepad++。
3. 完成后切换到普通记事本，再开始新会话，确认 TSF 路径仍可用且输入法布局不变。
4. x64 Notepad++（如安装）：与 x86 用例相同，确认兼容路径不依赖位数。
