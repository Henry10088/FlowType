# 通用文件传输设计

状态：功能已实现并完成发布构建验证；等待合并独立功能分支，不改变 V1 文字同步的架构和验收边界

最后修订：2026-09-07

## 1. 目标与原则

说写支持 Android 手机与已绑定 Windows 电脑之间的高性能双向文件传输：

- 手机可以发送多个文件、目录或混合批次到电脑，电脑自动保存，不弹接收确认。
- 电脑可以通过文件选择器、目录选择器或资源管理器拖放，发送多个文件、目录或混合批次到手机。
- 断网、应用进程退出或电脑重启后可以继续传输，不重复传输已经完成的文件。
- 文件传输不能阻塞实时文字输入或现有图片剪贴板传输。
- 不设置产品层面的单文件大小、批次总大小或文件数量上限；实现必须使用 64 位大小、流式清单和流式正文，所有内存、消息、路径和并发资源仍设置安全边界。
- 局域网不是可信边界，所有文件传输始终加密并认证，不提供明文或降低安全性的模式。

文件传输只面向已绑定电脑，不增加陌生设备广播发现，不提供公网中转。功能代码不进入注入助手或 TSF TIP，文件传输失败不能影响文字输入。

## 2. LocalSend 参考边界

实现重点参考 [LocalSend](https://github.com/localsend/localsend) 的开源代码和协议。设计基线为 2026-09-07 审查的 LocalSend `main` 提交 `6279d3e30d1d1290caee3b81549f8128a8b01d9f`。

采用的经验：

- 使用 HTTPS 请求直接流式传输二进制正文，不使用 Base64，不把完整文件载入内存。
- 先创建传输会话，再为文件授权；协议内核负责验证会话和文件身份，产品层决定自动接受或请求用户确认。
- 一次只有一个活跃接收会话，批次内使用有限并发和背压，取消后必须释放会话槽位。
- 文件状态、整体进度和失败项分开表达，单个文件失败不使已经成功的文件失效。
- 文件名按目标平台规则清理，正文写入使用有界缓冲并核对实际字节数。

不直接照搬的部分：

- 说写继续使用已有永久绑定、WSS 身份认证和电脑证书 SPKI 固定，不采用 LocalSend 的陌生设备发现、PIN 或可选 HTTP 模式。
- 传输令牌不放 URL 查询参数，统一放在授权请求头中，避免进入普通访问日志。
- LocalSend 当前上传会话和文件令牌主要面向一次在线传输；说写另外实现持久化批次、确认偏移和跨进程恢复。
- 不在传输前强制计算全部文件哈希，避免大批次长时间停留在“准备中”。

LocalSend 是重要实现参考，不是兼容目标。说写不承诺与 LocalSend 客户端互通。

## 3. 用户流程

### 3.1 手机到电脑

1. Android 支持系统文件选择器多选、系统目录选择器，以及从其它应用通过“分享”发送到说写。
2. 用户确认当前目标电脑后开始发送。只有用户主动选择或分享的批次可以触发电脑自动接收。
3. Windows 自动保存到 `%USERPROFILE%\Downloads\FlowType`，目录可在 Windows 设置中修改。
4. Windows 显示稳定的批次进度并发送系统通知，不自动打开、预览或执行收到的文件。
5. 文件和目录保持相对结构；同名目标不覆盖，使用批次开始时预留的唯一名称。

### 3.2 电脑到手机

1. Windows 文件传输页提供“选择文件”“选择文件夹”和资源管理器拖放。拖放可以混合文件与目录；系统选择器分别选择文件或目录后加入同一待发送批次。
2. Windows 显示当前目标手机，用户点击发送后，Android 收到一个批次请求。
3. Android 对整个批次只确认一次。确认界面显示电脑名、文件和目录数量、总大小、主要文件名及目标位置。
4. Android 记住通过系统目录选择器获得的持久目录授权。后续批次默认使用该目录，并允许在确认页“更改位置”；授权失效时才要求重新选择。
5. 应用在后台时使用通知提醒，用户点击通知进入确认页；电脑不能在手机无确认时静默写入。

### 3.3 队列、状态与取消

- 双方一次只运行一个活跃批次。一个批次支持多文件、目录或混合内容；传输期间禁用新的发起入口，避免为低频的多批次排队引入额外状态机和恢复复杂度。
- 批次内默认最多同时传输两个文件；活跃文字输入期间降为一个，不对单个大文件做多段并行。
- 状态固定为：`等待确认`、`排队中`、`准备中`、`传输中`、`等待网络`、`需要重新选择`、`已完成`、`部分失败`、`已取消`。
- 网络中断属于可恢复状态，界面停留在原位置，不反复闪烁错误或新建批次。
- 用户取消后删除未完成临时文件和恢复令牌，已经完成并原子提交的文件保留；批次结果明确列出已完成和未完成项目。
- 不提供手工暂停。切网、离线和进程退出统一进入“等待网络”，恢复后自动继续。

## 4. 文件和目录语义

- 清单项目使用稳定 `entry_id`，类型为文件或目录；显式记录目录以保留空目录。
- 目录传输默认包含被选择的目录名作为批次根目录，内部只传相对路径。
- 不跟随 Windows 快捷方式、符号链接、Junction 或其它 Reparse Point；Android 文档树只枚举选择树内由系统提供的文档节点。
- 拒绝绝对路径、`..`、NUL、路径分隔符注入和超出实现边界的路径。Windows 额外处理保留设备名、ADS 冒号、尾部句点或空格，以及不区分大小写的冲突。
- 目标名称在接收批次时一次性预留并持久化。根目录冲突时优先把整个根目录改为 `名称 (1)`，恢复时继续使用原目标，不重新计算名称。
- Windows 接收端尽力保留修改时间。Android SAF 提供方不保证允许修改时间，因此手机端修改时间只做尽力设置，不作为传输成功条件。
- 不复制 ACL、所有者、扩展属性、备用数据流或平台专有权限。
- 一个文件无法读取或源内容变化时标记该文件失败，继续其余文件，不无限自动重试正在变化的源文件。

## 5. 传输架构

### 5.1 控制面

现有 WSS/TLS 连接只传输：

- `file_offer`：批次 ID、方向、文件数、目录数、总大小、根名称摘要。
- `file_accept` / `file_reject`：批次确认结果。
- `file_ticket`：数据端口和短期批次能力令牌。
- `file_progress`：低频批次进度和当前文件摘要。
- `file_resume` / `file_resume_state`：恢复协商。
- `file_cancel` / `file_result`：取消和最终结果。

完整目录清单不进入 WSS。现有 1 MiB 文本消息上限保持不变，文件能力通过 `capabilities` 协商；旧客户端不支持文件能力时，文字和图片功能继续工作。

### 5.2 数据面

- 使用独立 HTTPS/TLS 1.3 端口和独立防火墙入口，复用 Windows 电脑身份和证书。
- Windows 始终作为数据服务端。手机上传使用 `POST`；电脑发送时 Android 通过出站 `GET` 拉取，Android 不开放入站端口。
- 使用 HTTP/1.1 长连接、二进制流式正文和有界背压，不要求 HTTP/2。
- 完整清单通过数据通道以分页 NDJSON 传输。单页有严格字节和条目上限，接收端边解析边持久化。
- 文件能力令牌通过 `Authorization` 请求头发送。令牌至少 256 位随机数，绑定电脑、手机、批次、方向和授权范围；令牌不绑定 IP，以允许 Wi-Fi、热点和 Tailscale 路径变化。
- 文件服务拥有独立连接信号量、磁盘任务和进度节流，不持有文字会话锁，不调用注入进程。

建议的数据接口语义：

- `POST /flowtype/files/v1/batches/{batch_id}/manifest`
- `POST /flowtype/files/v1/batches/{batch_id}/entries/{entry_id}`，手机上传，带起始偏移和剩余长度。
- `GET /flowtype/files/v1/batches/{batch_id}/entries/{entry_id}`，手机下载，支持标准 `Range`。
- `GET /flowtype/files/v1/batches/{batch_id}/state`
- `POST /flowtype/files/v1/batches/{batch_id}/complete`

路径中只使用随机批次 ID 和条目 ID，不出现原文件名。正文请求不使用 multipart，也不创建整批压缩包。

## 6. 断点续传与完整性

每个批次有稳定的 `batch_id`。发送端持久化源 URI 或路径、原始大小、修改时间和批次状态；接收端持久化已预留目标、临时路径、已确认偏移和文件状态。

- 接收端把正文写入目标目录同一文件系统中的随机 `.flowtype-*.part` 临时文件，避免跨磁盘原子替换失败。
- Android 文档提供方不支持可靠重命名时，优先使用目标树内临时文档；完成校验后尝试重命名，必要时复制到最终文档再删除临时文档。不默认把无限大小文件放入应用私有目录。
- 已确认偏移按“累计连续字节”表示。接收端约每 16 MiB 或每 1 秒刷新并持久化一次，以先到者为准；中断时允许重传最后一个未确认窗口。
- 恢复前重新核对源大小、修改时间和可访问性。来源发生变化时仅重置该文件，已经完成的其它文件不重传。
- 发送端和接收端传输时同时流式计算 SHA-256。正常传输不预读文件；恢复时双方重新读取已确认前缀以恢复哈希状态，然后继续网络传输。
- 无法重新定位或重新读取前缀的 Android 内容提供方只重传当前未完成文件，不影响已经完成的文件。
- 完成时比较总字节数和 SHA-256，校验通过后关闭临时文件、刷新到磁盘并原子提交为正式文件。
- 异常中断任务保留 7 天，保留期按最后一次活动时间计算；过期只清理恢复状态和临时文件，不删除已经完成的正式文件。

“支持断点续传”的产品边界是：源文件仍存在、内容未变化、目标仍可写且 Android URI 持久权限仍有效。权限或来源失效时进入“需要重新选择”，不能伪装成普通网络错误。

## 7. Android 后台和 SAF

- Android 14 及以上优先使用 User-Initiated Data Transfer Job 承载用户主动发起或确认的大文件传输。
- Android 10 至 13 使用 `dataSync` 前台服务和常驻进度通知。
- 两种执行方式共用同一持久化传输状态机，不把业务状态只放在 Activity、Service 或内存回调中。
- 发送文件和目录时请求并保存系统授予的持久 URI 权限；提供方不支持持久授权时，在开始前明确提示该批次无法跨进程恢复。
- 接收目录使用 `ACTION_OPEN_DOCUMENT_TREE` 的持久授权。系统禁止选择的根目录或特殊目录不通过自定义路径权限绕过。
- 进程或系统恢复任务时先核对 URI 权限和文件身份，再连接电脑；不能自动继续时保留任务并通知用户处理。

## 8. 安全设计

基础安全能力全部强制开启，UI 不提供“安全传输”开关：

- 控制面和数据面都只允许 TLS 1.3。
- Android 固定已绑定电脑的证书 SPKI；每次 WSS 连接继续验证手机绑定身份。
- 数据通道只接受通过已认证 WSS 签发的批次能力令牌。
- 批次令牌短期有效、可撤销、按方向和资源授权；恢复时可以通过重新认证换取新令牌。令牌不写普通日志、不进入 URL、不发送给第三方。
- 清单、文件名、相对路径、大小和正文都只在认证加密连接内传输。
- 接收端限制连接数、请求头大小、路径长度、清单页大小、同时打开文件数和排队批次数，防止已绑定但异常的设备耗尽资源。
- 手机到电脑自动保存只对手机用户主动创建的批次生效；Windows 预检查目标目录和磁盘空间，不自动打开或执行文件。
- 电脑到手机仍需用户对整个批次确认，避免电脑程序静默写入手机。
- Android Keystore 和 Windows 当前用户 DPAPI 保护持久化令牌等秘密；非秘密的传输元数据使用应用私有目录和当前用户 ACL。

## 9. 性能与资源策略

- 网络读取、磁盘写入和进度通知之间使用有界队列形成背压。
- 单文件缓冲建议 256 KiB 至 1 MiB；批次内最多两个文件并发，默认不压缩正文。
- 目录枚举、清单传输和 UI 展示都使用分页，不把所有条目复制成多个内存列表。
- 进度持久化最多每秒一次；UI 更新建议每 200 至 500 ms 一次，不随每个网络块重绘。
- 开始前根据清单总大小检查目标可用空间；空间不足时不开始正文，传输途中空间耗尽则保留可恢复状态。
- 活跃文字输入期间文件并发降为一，并保证 WSS 事件循环、注入 IPC 和文件磁盘任务之间没有同步锁依赖。

## 10. 包体积预算

当前 Release 基线约为 Android APK 0.94 MiB、Windows 安装包 3.18 MiB。实现优先复用 Android 已有 OkHttp、SQLite 和系统 SAF，Windows 复用 Tokio、rustls、SHA-256 和现有原子文件能力。

预算而非承诺：

| 组件 | 建议预算 | 约束 |
| --- | ---: | --- |
| Android APK | 增加 100-300 KiB | 不引入 Compose、Room、WorkManager 或媒体处理框架 |
| Windows 主程序 | 安装包增加 300-900 KiB | 使用最小 HTTP/1.1 服务特性，避免全功能 Web 框架和 bundled SQLite |
| Windows 注入助手/TIP | 0 KiB | 文件功能不得进入注入组件 |

若采用完整 Hyper/Axum 功能集或 bundled SQLite，Windows 安装包可能额外增加约 1-2.5 MiB，需要重新评估收益。最终以干净 Release 构建和安装包实测为准。

## 11. 实现阶段与提交边界

功能作为一个完整版本交付，但开发内部按以下阶段独立提交和验证：

1. 协议、路径规则、批次状态机、令牌和持久化格式。
2. 独立 HTTPS 数据服务、流式清单和 Android 到 Windows 自动接收。
3. Windows 拖放与选择、Android 批次确认、SAF 目标和 Windows 到 Android 下载。
4. 断点续传、进程恢复、电脑重启恢复、失败清单和队列。
5. Android 后台执行、系统通知、分享入口和完整产品 UI。
6. 安全、超大文件、十万级条目、弱网、磁盘不足、包体积和文字延迟验收。

任一阶段不得通过修改文字注入、TSF 或输入会话语义来解决文件问题。

## 11.1 实现结果

- 已完成 Android 到 Windows 的多文件、SAF 目录、空目录、中文和 Unicode 名称传输，Windows 自动保存到下载目录下的 FlowType 文件夹。
- 已完成 Windows 到 Android 的文件/目录选择、资源管理器拖放、整批确认和 SAF 保存目录持久授权。
- 已完成独立 TLS 1.3 数据通道、证书 SPKI 固定、短期批次令牌、流式 NDJSON 清单、64 位大小和 SHA-256 完整性校验。
- 已完成连续偏移断点续传、目标名称持久化、同名不覆盖、源变化检测、磁盘空间预检、取消和 7 天过期清理。
- Android 10 至 13 使用 dataSync 前台服务；Android 14 及以上使用用户发起的数据传输任务。传输活跃时保持控制连接，文字输入活跃时文件并发从两个降为一个。
- 大文件上传使用单次线性流式读取；接收端按 16 MiB 或 1 秒持久化确认偏移，避免按分块反复读取文件前缀造成平方级磁盘开销。
- Windows 安装器同时开放控制端口 32187 和加密文件数据端口 32188，范围仍限制为本地子网和 Tailscale 地址段。

发布构建实测：Android 未签名 Release APK 为 1,075,877 字节；Windows 未签名安装包为 3,418,584 字节。相对设计基线，Android 增量约 90 KiB；Windows 相对最近的 0.2.7 安装包增量约 84 KiB，均在预算内。

验证结果：Windows workspace 共 94 项自动测试通过（其中 5 项需要已注册 TIP 和交互式编辑器的测试按设计忽略）；Android JVM 测试、Debug AndroidTest 构建和 API 36 模拟器上的 5 项仪器测试通过，包含数据库 4→6、5→6 升级与传输目标字段持久化。

## 12. 验收条件

- 多文件、目录、空目录和混合拖放能够正确还原相对结构。
- 手机发送后 Windows 自动保存，不弹接收确认；电脑发送时 Android 只确认整个批次一次。
- 清单和正文均流式处理，大文件和大目录的内存使用不随总大小线性增长。
- 断网、双方应用进程退出和电脑重启后可以恢复；不可恢复的 Android URI 给出明确原因。
- 已完成文件不重复传输；断点只允许重传最后一个未确认窗口。
- 同名文件不覆盖，恢复后目标名称不变化，非法路径不能写出目标目录。
- 文件长度和 SHA-256 校验失败时不提交正式文件。
- 目标空间不足、源文件变化、权限失败、取消和部分失败都有稳定状态和失败清单。
- TLS 抓包看不到文件名或正文，未绑定设备和无效批次令牌不能访问数据接口。
- 文件传输期间文字同步 P95 延迟不明显恶化；活跃输入时文件并发自动降低。
- Windows 和 Android Release 包体积增量处于预算内，注入助手和 TIP 产物不增加文件传输依赖。
